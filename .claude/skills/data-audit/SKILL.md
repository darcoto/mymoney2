# Одит на данните

## 1. Пусни проверките (само четене)

```bash
node .claude/skills/data-audit/audit.js                     # data/finance.db + извлеченията в import/
node .claude/skills/data-audit/audit.js --db data/zz-test.db --files ""   # друга база, без сверка с файлове
```

Скриптът отваря базата **само за четене**. Ако сървърът работи (порт `PORT` или 3456), пита и
`POST /api/transactions/reconcile-imports` с `dryRun: true` — какво би поправило „Провери за дубликати“.
Логовете от backend модулите (`[20..] [INFO] ...`) филтрирай с `| grep -v '^\[20'`.

## 2. Как да четеш резултата

| Секция | Какво е проблем | Какво е нормално |
|---|---|---|
| 1. Сметки | месеци без транзакции при активна сметка → празнина в данните от банката (импортирай `.xls`/`.csv` за периода) | USD/джоб без движение някои месеци |
| 2. Файлове ↔ база | ненулеви редове без двойка, липсващи от файла | нулеви суми; ±1 ден в датата; неосчетоводени редове от файла (пропускат се умишлено) |
| 3. Наличност Revolut | последната наличност ≠ наличността на сметката; прекъсвания в последните месеци | прекъсвания в края на 2025 г. (портфейли в BGN и EUR в една сметка до 17.12.2025) |
| 4. Банкови записи | описание/контрагент различни от `raw_data`; блокирани суми; валута ≠ валутата на сметката; Revolut импорт без таксата | — |
| 5. Дубликати | неразличими повторения (без различен баланс/час); dry run с ненулеви числа | нулеви суми (проверка на карта); картови плащания с плюс с `MovementType: Credit` (възстановени суми) |
| 6. Категории | преводи между собствени сметки без категория тип `transfer` (отчетите ги броят като разход/приход) | без категория (информативно); „Работа обяд“ с плюс (колеги връщат пари) |

Разходи с приходна категория са **решение на потребителя** — само ги докладвай.
Навиците на потребителя при категоризиране (кои преводи са наем, дългове, детски, кои входящи са заплата и т.н.) са в `HABITS.local.md` в тази папка — локален файл, не е в git (съдържа имена). Прочети го преди да предлагаш прекатегоризиране; ако липсва — питай потребителя.

## 3. Поправки — само с изрично съгласие на потребителя

- **Никога не пиши в `data/finance.db` без съгласие.** Първо пробвай поправката на копие (`cp data/finance.db data/zz-test.db`, после изтрий копието).
- Преди запис: архив — `curl -s -X POST localhost:3456/api/backup` (или `cp -p data/finance.db data/backups/finance_before_<какво>_<дата>.db`).
- Повечето проблеми от секции 4–5 се поправят от приложението: Настройки → „Провери за дубликати“ → „Обедини“ (или `reconcileImportedTransactions({ dryRun: false })` от `backend/transaction-matching.js`). Същото се пуска и автоматично след всяка синхронизация.
- Описание/контрагент ≠ `raw_data`: обнови от `raw_data` с `transactionDescription()` / `transactionCounterparty()` от `backend/providers/gocardless-provider.js` (категорията и бележките не се пипат).
- Категории: през API (`PUT /api/transactions/:id/category`, `POST /api/categorization-rules`), не с директен SQL.
  **Кирилица — само през Node (`fetch`), не с `curl` от Git Bash:** той изпраща текста в грешна кодировка и в базата се записва „???“.
- Шаблоните на правилата са подниз без граници на думи: не ползвай къси шаблони (напр. „A1“ хващаше кодове за авторизация и магистрали A10/A11).
- След поправка пусни одита отново — трябва да покаже `Общо проблеми: 0`.

## 4. Когато добавяш нова проверка

Добави я в `audit.js` в съответната секция: `problem()` за грешка, `note()` за информативно, `ok()` за чисто.
Известните капани на банките са описани в `CLAUDE.md` (блокирани суми при ДСК, джобове и масив с текст при Revolut, BGN/EUR).
